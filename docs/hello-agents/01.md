## 习题 1 · 四 Case 是否为智能体及类型判定

### 1.1 Case A：2EFlop 超级计算机 —— ❌ 不是智能体

| 判定项 | 分析 |
| --- | --- |
| 是否智能体 | **否**（只是一台高性能计算硬件） |
| 理由 | 它拥有峰值算力，但**没有感知环境、没有目标导向、没有自主的感知–行动闭环**。它只是被动执行人类程序的「计算工具」，不会根据环境状态自主决策。 |
| 维度对照 | 无论算力多高，若内部无决策逻辑、不与环境交互，就**不落入任何智能体类型**——算力 ≠ 智能。 |

**启示**：智能体的本质是「**自主决策闭环**」，而非「强大算力」。冯·诺依曼结构只是硬件底座。

### 1.2 Case B：特斯拉自动驾驶遇障毫秒决策 —— ✅ 是智能体（反应式 + 基于模型/目标）

- **是否智能体**：✅ 是。它持续**感知**（摄像头/雷达）→ **决策**（刹车或变道）→ **行动**（控制转向/制动）→ **观察**（障碍是否避开）。
- **内部架构维度**：拥有**世界模型**（隧道中仍可推断前车位置/速度，§1.1.1 的「基于模型」），目标是**安全抵达目的地**（基于目标）；端到端神经网络使其为**学习型**智能体。
- **时间–反应性维度**：毫秒级避障以**反应式**为主，但路径规划又含**规划式**成分 → 属**混合式**。
- **知识表示维度**：以**亚符号主义**（深度学习神经网络）为主，叠加规则化的安全约束。
- **理由**：实时闭环 + 世界模型 + 安全目标，完全契合智能体定义；强调「毫秒级」正对应教材所说反应式智能体「速度快、计算开销低」的优势（如安全气囊）。

### 1.3 Case C：AlphaGo 评估局面、规划数十步 —— ✅ 是智能体（规划式 + 基于目标/效用）

- **是否智能体**：✅ 是。对弈即与环境（对手/棋盘）持续交互：感知棋面 → 规划落子序列 → 行动 → 观察结果。
- **内部架构维度**：**基于目标**（赢棋）+ **基于效用**（以胜率/价值网络评估局面）；具备**世界模型**（棋盘状态）。
- **时间–反应性维度**：评估数十步 → 典型**规划式（Deliberative）**智能体，类同教材「棋手预想后续十几步」。
- **知识表示维度**：**神经符号混合**——策略/价值网络（亚符号）做直觉评估，MCTS 树搜索（符号化前瞻）做逻辑推理；且经**强化学习**自我对弈进化（学习型）。
- **理由**：需要长远规划、效用权衡与学习，是规划式 + 神经符号 + 学习型的综合范例。

### 1.4 Case D：ChatGPT 智能客服处理投诉 —— ✅ 是智能体（混合式 LLM 智能体）

- **是否智能体**：✅ 是。它**查询订单（工具调用）→ 分析问题（推理）→ 提供方案（行动）→ 安抚情绪（生成）**，并在多轮中根据用户信息持续调整——典型的 **LLM 智能体**运作（§1.1.2）。
- **内部架构维度**：**基于目标**（解决投诉）+ **基于效用**（最大化用户满意度）；可通过 RLHF 微调获得**学习能力**。
- **时间–反应性维度**：在「思考–行动–观察」循环中既**规划**（拆解问题）又**反应**（即时调用工具），属**混合式**。
- **知识表示维度**：内核为**亚符号**（LLM 神经网络），但通过结构化 API 调用引入**符号化**操作 → **神经符号主义**实践。
- **理由**：兼具语义理解、工具使用与动态修正，是教材所述「LLM 智能体把规划与反应融为一体」的 directly 例证。

**小结**：四例中，**只有 A 不是智能体**——算力再大也只是工具；B/C/D 均为智能体，但分别偏重反应式、规划式、混合式，知识表示上从亚符号到神经符号递进。

## 习题 2 · 智能健身教练的 PEAS 与环境特性

### 2.1 PEAS 描述

| PEAS 维度 | 智能健身教练的具体内容 |
| --- | --- |
| **P · 性能度量** | ① 训练目标达成度（减脂体重/体脂率、增肌围度、耐力 VO₂max 提升）；② 动作规范性（纠错及时率）；③ 用户安全（运动伤害发生率↓）；④ 用户依从度与满意度（课程完成率、续订率） |
| **E · 环境** | 用户的物理身体状态、家庭/健身房运动空间、可穿戴设备数据流、营养与饮食环境、天气/作息等外部约束 |
| **A · 执行器** | 语音播报（实时指导/纠正）、App 界面（计划推送/图表）、可穿戴设备震动/提示、与智能器械的联动控制、饮食建议推送 |
| **S · 传感器** | 可穿戴设备（心率带/手环：心率、HRV、步频、卡路里）、加速度计/陀螺仪（动作幅度、姿态）、用户输入（目标设定、疲劳自评）、可能的摄像头（动作姿态识别） |

### 2.2 环境特性分析

- **部分可观察（Partially Observable）** ⭐：教练**无法**直接看见用户肌肉微损伤、真实疲劳阈值或隐藏疾病，只能从心率/动作等**间接信号**推断。这要求智能体具备**记忆**（记住历史训练负荷）与**探索**（逐步试探强度上限），教材正是用「旅行助手查不到全部航班余票」说明此特性。
- **随机性（Stochastic）** ⭐：同一套计划，用户今天和明天的恢复状态、心率响应都可能不同；饮食与睡眠等外部因素引入噪声。环境**非确定性**，智能体需监控变化、具备容错与动态调整能力。
- **多智能体（Multi-agent）** ⭐：环境中存在「其他行动者」——用户的私人教练、同健身房的器械调度、甚至用户的社交圈（同伴打卡影响动机），它们的动作会改变本智能体所处状态，要求快速响应。
- **序贯 + 动态（Sequential & Dynamic）** ⭐：「序贯」指本次训练强度影响下次恢复；「动态」指环境在教练决策时仍在变化（心率实时波动）。因此「感知–思考–行动–观察」循环必须**快速、灵活**地适应（§1.2.2）。

**小结**：这是一个**部分可观察、随机、多智能体、序贯且动态**的典型复杂环境。正因如此，纯规则（if 心率>阈值则降强度）难以胜任，更适合 **LLM 智能体 + 世界模型 + 在线学习** 的方案——它能在不确定中规划、在反馈中动态修正（呼应 §1.1.2 的「动态修正」能力）。

## 习题 3 · 电商售后退款：Workflow（方案 A）vs Agent（方案 B）

### 3.1 两种方案各自的优缺点

| 维度 | 方案 A：Workflow（固定规则） | 方案 B：Agent（智能体） |
| --- | --- | --- |
| **可控性** | ✅ 极强，决策路径完全可预期、可审计 | ⚠️ 较弱，存在「黑箱」决策，需额外可解释性设计 |
| **一致性/公平性** | ✅ 同条件必同结果，避免人工与模型波动 | ⚠️ 同样输入可能因模型随机性给出不同结论 |
| **可维护性** | ⚠️ 规则爆炸：金额/天数/品类组合一旦增多，嵌套 if 极难维护（呼应第二章「组合爆炸」） | ✅ 政策变动只需更新 Prompt/知识库，无需重写分支 |
| **长尾处理** | ❌ 未覆盖的特殊情况一律卡死或误判 | ✅ 能理解「商品已拆封但属质量问题」等模糊情形 |
| **成本/时延** | ✅ 廉价、毫秒级 | ⚠️ 每次 LLM 推理有 token 成本与延迟 |
| **风险/合规** | ✅ 不会「幻觉」擅自批大额 | ⚠️ 可能幻觉越权、误批，需护栏（guardrails） |

### 3.2 何时 Workflow 更合适？何时 Agent 更有优势？

- **Workflow 更合适**：
  - 规则边界清晰、高频且标准化（如 7 天内 <100 元自动通过）；
  - 对**合规与可审计性要求极高**（金融、医疗审批）；
  - 成本敏感、需低延迟、且长尾占比极低。
- **Agent 更有优势**：
  - 存在大量**模糊语义**（「用户历史行为良好但本次描述含糊」「商品状况需综合判断」）；
  - 政策频繁变化、规则组合爆炸；
  - 需要**多步推理 + 工具调用**（查订单、查聊天记录、查物流、评估信用）才能决策。

### 3.3 作为负责人，我倾向哪种？

**倾向**：**以 Workflow 为底座、Agent 做兜底与疑难升级的混合方案（即方案 C）**。纯 Agent 直接掌握退款「钱袋子」风险过高；纯 Workflow 又会在长尾上大量误杀/人工兜底，体验差。先用确定性规则覆盖 80% 标准单，把 Agent 解放出来处理真正需要理解的 20% 疑难单，性价比与风险最优。

### 3.4 方案 C：扬长避短的混合架构

```
┌─────────────────────────────────────────────┐
│  入口：退款请求                               │
└───────────────┬─────────────────────────────┘
                ▼
┌─────────────────────────────────────────────┐
│ ① 规则引擎 (Workflow) — 高置信度快通路        │
│   标准商品 & 7天内 & <100 → 自动通过           │
│   定制品 → 自动拒绝                           │
│   命中明确分支 → 直接执行，结束               │
└───────────────┬─────────────────────────────┘
                │ 未命中 / 低置信度
                ▼
┌─────────────────────────────────────────────┐
│ ② 智能体 (Agent) — 疑难单深度决策             │
│   工具：查订单/物流/聊天记录/信用分           │
│   推理：政策理解 + 用户历史 + 商品状况         │
│   输出：建议(approve/reject/转人工) + 理由    │
└───────────────┬─────────────────────────────┘
                ▼
┌─────────────────────────────────────────────┐
│ ③ 护栏 (Guardrails) — 硬约束兜底              │
│   大额(>500) 强制转人工主管审批               │
│   拒绝必须附可解释理由；异常触发告警           │
└─────────────────────────────────────────────┘
```

**效果**：**确定性快、长尾准、风险可控**。Agent 在「需要理解」的环节发挥价值，而「不能出错」的环节由 Workflow 与护栏牢牢守住——正是教材 §1.4 所述「让智能体在合适的位置协作」的体现。

## 习题 4 · 扩展 1.3 旅行助手：记忆 / 售罄备选 / 拒绝反思

### 4.1 功能一：「记忆」——记住用户偏好

**设计思路**：在循环外引入一个**持久化记忆体 `memory`**（字典 / 向量库 / 数据库），并在三个位置接入：

```python
# 1) 初始化时加载历史偏好
memory = load_user_profile(user_id)   # {"likes": ["历史文化"], "budget": "200-500", "avoid": ["拥挤"]}

# 2) 每轮 Thought 前，把 memory 注入 Prompt（作为长期记忆）
prompt = build_prompt(goal, history, observation, memory=memory)

# 3) 当 Observation 中暴露新偏好（如用户说"我喜欢安静古镇"），写入记忆
if "喜欢" in observation or "偏好" in observation:
    memory.update(extract_preference(observation))   # 结构化抽取
    save_user_profile(user_id, memory)
```

- **闭环改动**：`感知` 阶段增加 `memory` 输入；`行动` 后若 Observation 含偏好信号，则触发 `记忆更新`。这恰好回应教材 §1.2.1 所说「部分可观察环境要求智能体具备记忆」。
- **作用**：后续推荐天然符合预算/兴趣，减少重复问答，体现 LLM 智能体的「动态修正 + 上下文利用」。

### 4.2 功能二：门票售罄 → 自动推荐备选

**设计思路**：将其建模为**工具返回异常 → 重新规划**的标准 ReAct 分支。

```python
# 工具层新增「余票查询」与「同类景点检索」
def action_query_ticket(spot):
    stock = ticket_api.check(spot)
    return stock if stock > 0 else "SOLD_OUT"   # Observation 显式返回售罄

# Thought 阶段判定：若 Observation == "SOLD_OUT"
#   → 不 Finish，而是发起新 Action: action_similar_spots(spot, memory)
#   → Observation 返回备选列表 → 继续比较
```

- **闭环改动**：在 `思考` 阶段加入**「售罄即转备选」规则**：当 Observation 标识资源不可用，规划器自动派生「相似景点检索」子目标，而非报错终止。这正是教材 `行动→环境状态变化→新 Observation→下一轮循环` 的范例。

### 4.3 功能三：连续拒绝 3 次 → 反思并调整策略

**设计思路**：维护一个**拒绝计数器 `reject_count`**，并在循环内加入**反思（Reflection）分支**。

```python
reject_count = 0
for i in range(MAX_STEP):
    thought, action = llm(prompt, memory, reject_count)   # 把拒绝次数也喂给模型
    obs = run(action)
    if action.is_reject_feedback(obs):      # 用户表达"不喜欢/再换一个"
        reject_count += 1
        if reject_count >= 3:
            # 触发反思：让 LLM 总结前 3 次被拒原因，调整推荐策略
           反思 = llm.reflect(history, memory)
            prompt += f"\n[反思]{反思}：请换一种思路（如避开已推荐类型/放宽预算）"
            reject_count = 0                # 重置，避免无限循环
    else:
        reject_count = 0
```

- **闭环改动**：把 `reject_count` 与 `反思结论` 作为**新 Observation/约束**注入下一轮 Thought，使规划器「从失败中学习」——这是「学习型智能体」（§1.1.1 演进顶端）的轻量实现。
- **安全阀**：重置计数器 + 保留 `MAX_STEP` 上限，防止反思后仍无休止重试。

**三项改动总结**：① 加**记忆模块**（long-term state）；② 把售罄/拒绝等 Observation 显式结构化，让**规划器能派生新子目标**；③ 引入**反思提示**与计数器。核心都是「在不破坏 Thought→Action→Observation 主循环的前提下，丰富状态与工具」。

## 习题 5 · 卡尼曼系统 1 / 系统 2 与神经符号主义

### 5.1 落地场景：智能医疗诊断助手（分诊 + 辅助诊断）

该助手接收患者主诉（文本/可穿戴体征），结合电子病历，输出**分诊级别 + 疑似诊断 + 依据 + 转诊建议**。

### 5.2 哪些任务由「系统 1」处理（亚符号 / 快速直觉）

- **症状意图分类**：把"胸口闷、喘不上气"快速归类为「心肺相关主诉」——类似模式匹配，无需逐步推理。
- **体征异常初筛**：根据可穿戴心率/血氧，毫秒级判断是否越界（如 SpO₂<90% 直接触发高危标记）。
- **紧急度粗判**：看到「胸痛 + 冷汗」立刻联想到急性冠脉综合征的"直觉预警"（经大量病历预训练获得的模式）。
- **自然语言理解**：把口语化主诉映射到标准化医学概念（ICD 编码雏形）。

- **亚符号主义**（连接主义）擅长模式识别与语言生成，速度快、无需显式规则——正是系统 1。

### 5.3 哪些任务由「系统 2」处理（符号 / 慢速推理）

- **鉴别诊断推理**：当症状重叠（发热+皮疹 既可能是麻疹也可能是过敏），用**知识图谱 + 贝叶斯推理**逐步排除，输出带概率的鉴别诊断树。
- **用药冲突核查**：调用**规则引擎/符号知识库**（药物-疾病-相互作用表）严格校验处方合法性——必须可解释、零容错。
- **诊疗路径规划**：生成「先查血象 → 再影像 → 必要时会诊」的有序计划（规划式智能体）。
- **可追溯决策**：产出"为何建议转诊"的可读论证，供医生审核（符号化、可审计）。

- **符号主义**擅长确定性推理与可解释逻辑——正是系统 2，且是医疗这种高风险领域不可省略的一环。

### 5.4 两系统如何协同达成目标（神经符号融合）

```
患者主诉/体征
      │
      ▼
┌─────────────── 系统 1（亚符号/LLM 直觉）──────────────┐
│ 快速理解主诉 + 体征初筛 + 紧急度粗判 → 生成"初步假设" │
└───────────────────────┬──────────────────────────────┘
                        │ 初步假设（结构化中间步骤）
                        ▼
┌─────────────── 系统 2（符号/规则+推理）───────────────┐
│ 用知识图谱/贝叶斯做鉴别诊断；用规则引擎核查用药冲突； │
│ 规划检查路径；产出可解释结论                          │
└───────────────────────┬──────────────────────────────┘
                        │ 若系统2发现矛盾/低置信度
                        ▼
              回灌系统1 → 重新提问/补充检查（循环修正）
                        │
                        ▼
              最终：分诊级别 + 诊断 + 依据（医生复核）
```

- **协同要点**：系统 1 **快而广**地缩小搜索空间、理解模糊输入；系统 2 **慢而严**地做确定性推理与合规校验；二者通过「结构化中间步骤」（教材说的 Thought/Plan/API call）衔接，形成「**直觉定位 → 符号验证 → 反馈精炼**」的闭环。
- **为何必须融合**：纯系统 1（裸 LLM）易幻觉、不可审计，不能单独下医疗结论；纯系统 2（老式专家系统）难以理解自由文本、知识获取瓶颈严重（见第二章 MYCIN）。**神经符号 = 系统 1 + 系统 2**，兼顾自然理解与可靠推理，正对应教材「真正鲁棒的 AI 需兼具二者之长」。

## 习题 6 · 智能体系统的局限与评估

### 6.1 为什么会产生「幻觉」？（生成看似合理却错误的信息）

结合教材 §1.1.2 对 LLM 局限的描述（亚符号不透明、纯逻辑推理易出错），幻觉根因可归为三层：

1. **表征本质是「统计模式」而非「事实符号」**：LLM 是**亚符号**神经网络，学到的是 token 间的条件概率分布，"合理"≠"真实"。它会生成"最顺滑的续写"，而非"经核实的事实"（教材指出它"无法解释为什么认为这是猫"）。
2. **训练数据本身有噪声/偏见/知识截止**：模型在预训练时吸收了互联网错误信息与过时知识，调用时无法区分"广为人知的事实"与"罕见但被错误复述的内容"。
3. **缺乏 grounding（ grounding 到真实环境/工具）**：当智能体**只靠参数记忆回答、未调用工具/检索**时，面对知识盲区便"编造"以填补连贯性——尤其在强制必须给出答案的 Prompt 下更严重。
4. **推理链过长触发误差累积**：多步 ReAct 循环中，一旦某步 Thought 出错，后续会基于错误前提继续"自圆其说"，幻觉被链式放大。

缓解思路：**让系统 2（符号/工具）介入**——通过检索增强（RAG）、工具校验、知识图谱约束，把"直觉续写"锚定到可验证事实。

### 6.2 若 1.3 案例去掉「最大 5 次循环」限制，会陷入什么？

教材 §1.3 设 `range(5)` 是为防止无限循环。移除后可能出现三类问题：

- **死循环（Loop）**：当工具持续返回失败时（如 API 报错、景点始终售罄），智能体可能反复 `Action→失败 Observation→再 Action`，永不 `Finish`。
- **目标漂移（Goal Drift）**：长循环中，模型逐步"忘记"初始目标，被中间 Observation 带偏，最终答非所问或过度展开。
- **成本与延迟失控**：每轮都调用 LLM + 工具，无限循环意味着 **token 费用与响应时间无界增长**，甚至触发限流/超时。
- **错误累积放大**：如 6.1 所述，循环越久，幻觉与误判被逐步累积，最终输出反而更不可信。

因此需要 **最大步数（budget）+ 早停（early-stop）+ 失败计数兜底** 等护栏——它们是 Agent Loop 可靠运行的"断路器"。

### 6.3 如何评估「智能」？仅准确率是否足够？

**显然不足。** 准确率只衡量"单次输出对不对"，而智能体是**在部分可观察、随机、多智能体、序贯动态**环境中**持续决策**的系统（§1.2.1）。更全面的评估维度：

| 维度 | 说明 | 为何超越准确率 |
| --- | --- | --- |
| **任务成功率 / 目标达成率** | 最终是否完成用户目标（如订到符合预算的票） | 比"每轮对错"更贴近真实价值 |
| **效率（步数 / token / 时延）** | 达成目标用了几轮循环、多少成本 | 衡量"聪明"而非仅"正确" |
| **鲁棒性 / 容错** | 工具失败、Observation 异常时能否恢复 | 开放环境必备 |
| **泛化性** | 未见过的长尾场景能否处理 | 避免过拟合到训练分布 |
| **可解释性** | 决策能否给出可追溯理由（系统 2） | 高风险领域合规刚需 |
| **安全性 / 价值对齐** | 是否越权、产生有害/幻觉输出 | "正确但危险"不可接受 |
| **人机协作满意度** | 用户主观体验、信任度 | 最终落地指标 |

**结论**：准确率是**必要非充分**指标。对智能体应构建「**成功率 × 效率 × 鲁棒性 × 安全/可解释**」的多维评估体系，并与 §1.4 的「作为开发者工具 / 作为自主协作者」两类定位相匹配（协作型更重人机满意度，自主型更重成功率与安全性）。
